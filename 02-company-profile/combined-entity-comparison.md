# Nordhaven And LumaPay Comparison

## Purpose
This comparison helps explain why the acquisition is an AI risk stress test rather than a simple control uplift exercise.

| Area | LumaPay | Nordhaven | Integration Risk |
| --- | --- | --- | --- |
| Size | `200` employees | `10,000` employees | Large maturity and operating-model gap |
| Engineering Capacity | `100` developers | Larger enterprise engineering estate | LumaPay can ship quickly but with weaker guardrails |
| Platform Capacity | `5` platform engineers | Mature platform and support functions assumed | Thin LumaPay foundations create dependency bottlenecks |
| Security Team | No dedicated security team | Dedicated security team | Immediate oversight and ownership mismatch |
| GRC Capability | Immature and fragmented | Dedicated security GRC team | Policy and evidence expectations diverge sharply |
| Risk Process | Informal or limited | Established enterprise risk process | Risk acceptance and escalation may be inconsistent |
| Cloud Security Tooling | No `CSPM` | `CSPM` in place | Posture visibility gap |
| Data Security Tooling | No `DSPM` | `DSPM` in place | Data inventory and control gap |
| AI Security Tooling | No modern AI security tools | Modern AI security tools in place | LLM and agent risk coverage gap |
| AI Governance | Partial documentation and limited lifecycle controls | More mature governance baseline | Transitional accountability gap |

## Interpretation
The core problem is not only that LumaPay is less mature. The bigger issue is that Nordhaven inherits an AI estate whose control assumptions, documentation quality, and operational tempo were built without the tooling, staffing, and governance depth Nordhaven would normally require.
